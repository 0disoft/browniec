# M1 i64 Scalars

- Status: implemented and verified for its slice; historical after the unsigned increment; 49 native groups and 760 CLI cases in each development and release profile
- Scope: full-width signed i64 scalars in `brownie.m1-scalar/1`

This historical increment extends the existing i32, bool, branch, loop, shallow
tagged, and `?` slices with `i64` values. The unsigned increment now extends the
same positions with `u8`, `u32`, and 64-bit guest `usize`. The entry point remains
exactly `fn i32 main()` with no parameters.

## Source contract

`i64` is an ordinary scalar type. It may be used in function parameters and
results, call arguments and returns, typed locals, assignments, loop variables and
expressions, and switch-expression result joins. Integer operator rules require
two operands of the same integer type. There are no implicit i32/i64 conversions,
casts, or literal suffixes. Bool remains a separate type.

The shallow Option/Result families are unchanged. Their payloads remain i32 or
bool, so `Option<i64>` and every `Result` containing i64 are rejected. Functions
returning i64 reject postfix `?`; propagation remains limited to functions returning
an admitted i32/bool wrapper.

Classic `for` headers remain pure scalar code. The init accepts an i64 declaration
or assignment; the post accepts an assignment only, and the condition remains bool.
Direct calls, postfix `?`, and switch expressions remain forbidden in all three
header clauses.

## Literals and context

An unsuffixed decimal literal defaults to i32. It is admitted as i64 when the
expected type comes from a typed initializer, assignment target, function argument,
function return, or the already typed left operand of a binary expression. The
accepted range is:

```text
-9223372036854775808 .. 9223372036854775807
```

Typing is left to right with no lookahead. These are accepted because `n64` gives
the right literal an i64 context:

```text
n64 + 1
n64 == 1
```

This is rejected because the context-free left literal is already i32 when the
right operand is read:

```text
1 == n64
```

The magnitude 9223372036854775808 is accepted only directly after unary minus in
an i64 context, producing i64 MIN. The minimum and maximum are admitted as
`-9223372036854775808` and `9223372036854775807`; the bare positive minimum
magnitude, values beyond either bound, and `-(9223372036854775808)` are rejected.
The scanner accumulates digits negatively and records the minimum magnitude with a
sentinel so scanning does not overflow a signed i64. That negative-accumulation
rule belongs to this historical i64 slice; the current unsigned scanner uses the
prechecked magnitude rule in the [unsigned contract](m1-unsigned.md).

## Arithmetic and evaluation

Unary `-` and binary `+`, `-`, `*`, `/`, and `%` support i64 with exact i64
operands and an i64 result. Ordering produces bool, and equality and inequality
accept i64 with i64. Operands evaluate once from left to right. Arithmetic is
checked before the corresponding native signed operation.

Overflow is a guest failure. This includes i64 MIN divided or remaindered by -1;
the existing i32 equivalents overflow as well. Division and remainder by zero
produce the guest zero-divisor outcome. Signed division truncates toward zero and
the remainder follows the dividend. A checked failure preserves the first
left-to-right fault and does not become a native trap.

## Representation and limits

The private scalar tags are 1 for i32, 2 for bool, and 9 for i64. The six shallow
wrapper tags remain 3 through 8, and the later unsigned increment uses tags 10
through 12. Registers and constants were already i64 cells, so
this increment adds no guest register widening, heap allocation, opcode, cap, or
Fuel-policy change. Existing instruction, register, constant, source, token,
binding, function, call, loop, and frame limits are unchanged.

The verifier checks i64 instruction and call metadata like the other scalars and
retains the i32 range check only for i32 constants. The existing Fuel schedule
applies without an i64 surcharge. For example, binding `6 * 7` into an i64 local and
then returning i32 42 costs 5 Fuel and fails at 4.

The implementation adapts checked signed arithmetic guards from the existing M0
probe into [`src/arithmetic.fy`](../../src/arithmetic.fy); the original M0 probe
remains unchanged.

## Example and evidence

`examples/i64.brc` uses i64 parameters, returns, locals, assignment, comparisons,
and a switch-expression join, then returns guest i32 42 from `main`.

```powershell
./build/browniec.exe run examples/i64.brc --json
```

The [dated receipt](../evidence/m1-i64-windows-20261023.json) is historical after
the unsigned increment and records 49 native groups and 760 CLI cases in both
development and release. The [unsigned receipt](../evidence/m1-unsigned-windows-20261023.json) records
59 native groups and 1,159 CLI cases in both profiles, adding 399 CLI cases. The i64 slice uses source commit `126c680`; M0's 18
recorded inputs and compiler identity remain unchanged.

The slice makes no performance claim and does not establish full M1,
`brownie.safe/0.3` conformance, richer value-arm statements, workers, DLL embedding,
or Windows isolation.
